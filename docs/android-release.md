# Local Android signing and upgrade identity

Maintainer decision (2026-09-13): **sign locally; never upload the release private
key to GitHub or ordinary CI**. Keep a separately encrypted offline backup under
the maintainer's control. No production key has been generated by this work.

This is release preparation, not approval to publish, install, replace the phone
app, create a tag, or clear data. APK inspection cannot certify application-level
upgrade behavior, Android Keystore retention, SAF grants or 16 KiB-device behavior.

## Identity and versions

- The existing debug app and the proposed release both use `io.mirelay.android`.
  No package suffix, database schema, token key alias or directory permission is
  changed here. Default debug builds remain versionName `0.1.0-dev`, versionCode 1.
  Always use `android/scripts/build.sh` for debug builds: it consistently sets
  `ANDROID_USER_HOME=android/.local/android-user`. A standalone Gradle invocation
  with another Android user home can select a different debug keystore and make
  its APK unsuitable for updating the existing development installation.
- A release versionName must exactly match **both** Cargo package versions. The
  prepare tool reads those manifests; Gradle also rejects mismatched metadata.
  Accepted versions are `X.Y.Z` and `X.Y.Z-alpha.N`, `-beta.N`, or `-rc.N`.
- The intended tag, when separately authorized, is `v<versionName>`. There is no
  automatic tag or Release creation. Before choosing `0.1.0-beta.1`, update both
  Cargo versions and their lockfiles together and freeze/revalidate that source.
  The current `0.1.0` metadata is not a declaration of stable readiness.
- versionCode is explicitly supplied, between 2 and 2100000000. Reserve a strictly
  greater code for each distributed APK, including prereleases and rebuilt
  artifacts; never reset it when versionName changes. The first test uses code 2,
  not a distributed version. Keep a distribution ledger before the first release.

Android uses versionCode for downgrade protection; this workflow additionally
requires a strict increase for upgrade acceptance. See [Android versioning](https://developer.android.com/studio/publish/versioning).

## Key custody — maintainer action, outside chat

Create the key only in your own trusted terminal, outside the checkout and any
cloud-sync folder. The following commands are instructions, **not executed by
the preparation tool**. They refuse an existing key path; do not replace a key.
Use a long unique passphrase stored separately in your password manager. Do not
paste it, the keystore, or an exported private key into chat or CI configuration.

```bash
umask 077
mkdir -p "$HOME/.local/share/mirelay-signing"
chmod 700 "$HOME/.local/share/mirelay-signing"
test ! -e "$HOME/.local/share/mirelay-signing/release.p12" && \
  android/.local/jdk/bin/keytool -genkeypair -storetype PKCS12 \
    -keystore "$HOME/.local/share/mirelay-signing/release.p12" \
    -alias mirelay-release -keyalg RSA -keysize 3072 -validity 10000 \
    -dname 'CN=MiRelay'

# Read the public SHA-256 CERTIFICATE fingerprint, not the public-key hash.
android/.local/jdk/bin/keytool -list -v \
  -keystore "$HOME/.local/share/mirelay-signing/release.p12" \
  -alias mirelay-release
```

Keep the certificate fingerprint and alias in the maintainer's release ledger;
they are public identity, not signing capability. Verify an encrypted offline
backup can actually be opened and has the same certificate fingerprint before
distributing anything. Preserve the original debug keystore separately for
future consented legacy updates; **do not promote it to the release identity**.
Do not use key rotation as an untested migration shortcut.

Android's [signing documentation](https://developer.android.com/studio/publish/app-signing)
explains the relationship between signing identity and app updates. This initial
workflow intentionally accepts one exact certificate and no rotation lineage.

## Prepare without any private key

Requires Python 3.11+ and the existing repository-local SDK/JDK/NDK. From the
repository root, after freezing the source:

```bash
python3 android/scripts/release.py prepare --version-code 2
```

This rebuilds both native ABIs, creates an **unsigned release** APK and copies it
into a fresh private `android/.local/releases/candidate-*/` directory, alongside
`prepare.json`. It does not overwrite a previous prepared artifact. Gradle has
no release signing configuration and rejects release builds without explicit
valid metadata. No key or password is a Gradle property.

`--allow-dirty` is only for local unsigned development validation. Its report
explicitly records a dirty tree, not acceptance of HEAD or a frozen release.
Never use that result as a release-candidate provenance claim. Preparation may
download locked dependencies through the existing build workflow; it is not
guaranteed air-gapped. Signing/inspection itself does not initiate a download.

## Inspect, sign a copy, then verify

Read-only inspection can be used on the existing debug APK too. Exit 0 from
**inspect** only means inspection completed: a debug or unsigned APK is not
accepted as a release merely because its metadata was readable.

```bash
python3 android/scripts/release.py inspect /absolute/path/to/unsigned.apk
```

After reviewing its hash, version, source identity and the trusted public
certificate fingerprint, run signing in **your own interactive terminal**:

```bash
python3 android/scripts/release.py sign /absolute/path/to/unsigned.apk \
  --version 0.1.0 --version-code 2 \
  --apk-sha256 REVIEWED_UNSIGNED_APK_SHA256 \
  --certificate-sha256 REVIEWED_CERTIFICATE_SHA256 \
  --keystore "$HOME/.local/share/mirelay-signing/release.p12" \
  --alias mirelay-release
```

The placeholders must be replaced with the actual reviewed **public hashes**.
No private-key or password argument exists. Passwords are entered without echo
and passed to apksigner over stdin, not argv, files, Gradle or reports. Python
cannot guarantee secure password memory erasure; use a trusted local account.
The tool refuses CI/noninteractive signing and a symlink, repository-contained,
foreign-owned or group/world-accessible keystore.

It snapshots the reviewed input, aligns a new copy, signs to `unverified.apk`,
checks the actual certificate and metadata, and only then names it `signed.apk`
and records `verified.json`. On failure, any partial candidate directory remains
private for diagnosis; **do not distribute files without a successful verification
report**. The original APK is never rewritten. See [apksigner](https://developer.android.com/tools/apksigner)
and [zipalign](https://developer.android.com/tools/zipalign) for the required order.

```bash
python3 android/scripts/release.py verify /absolute/path/to/signed.apk \
  --version 0.1.0 --version-code 2 \
  --certificate-sha256 REVIEWED_CERTIFICATE_SHA256

# For a subsequent release, also require the previous accepted APK identity.
# Select the actual next version and a strictly greater versionCode first.
python3 android/scripts/release.py verify /absolute/path/to/next-signed.apk \
  --version NEXT_VERSION --version-code NEXT_CODE \
  --certificate-sha256 REVIEWED_CERTIFICATE_SHA256 \
  --previous-apk /absolute/path/to/previous-signed.apk
```

Checks cover actual package/version/SDK, non-debug identity, a valid signature
matching the exact certificate, ZIP 16 KiB alignment, both JNI ABIs, and every
packaged native library's ELF64 machine/LOAD alignment. SHA-256 is recorded for
the APK and all libraries, including third-party `.so` files. This is not a
substitute for testing the final APK on supported devices; see Android's
[16 KiB guidance](https://developer.android.com/guide/practices/page-sizes).

## Existing debug phone — migration remains blocked

The inspected local debug APK has Android Debug signing identity and code 1.
It is **not evidence of the currently installed phone APK**; no phone was queried
or changed in this work. A new release key must not be assumed to overwrite it.

1. Keep the existing installation and its debug identity intact. Do not uninstall,
   clear data, force a signature bypass, or use an emulator reset runner on it.
2. Before a future migration, obtain explicit phone permission; read the installed
   package/certificate/version and inventory Folder state and pending work without
   exporting plaintext tokens. Pause/drain work only with the owner's consent.
3. A tested authenticated export/import or a separately approved reinitialization
   route is still required. That implementation does **not** exist in this patch.
   Encrypted SQLite token values cannot simply be copied to a new installation:
   `TokenVault` depends on the app's Android Keystore key. A new app identity also
   needs user-mediated directory grants. Changing a package suffix is coexistence,
   not migration of these credentials, grants, receipts or pending tasks.
4. Validate fresh install and same-release-certificate upgrade on a disposable
   test device first; then separately verify Folder settings, real Keystore
   credentials, SAF access, histories, pending tasks, Auto and transfer receipts.
5. Only choose a real-phone transition after that path is implemented and tested.
   Keeping the debug version in service is the safe current default.

The [Android Keystore](https://developer.android.com/privacy-and-security/keystore)
protects non-exportable key material; the application's current backup exclusions
and lack of migration code are additional reasons not to promise a file-copy restore.
