## Findings

### P2 — Screenshot write failure aborts the process

Reproduced twice with an output path whose parent does not exist. `capture_widget` in `src/desktop.rs` returns early when `save_to_png` fails, before calling `renderer.unrealize()`. Dropping the still-realized renderer then triggers:

```text
Gsk:ERROR:gsk_renderer_dispose: assertion failed: (!priv->is_realized)
```

This affects the hidden developer screenshot workflow. It was **not** observed during normal receive, sorting, filtering, or restart tests. An I/O error should produce an ordinary error exit, not a signal-terminated process. The regression test checks both conditions, so an abort cannot masquerade as successful error handling.

Reproduce (requires a graphical session; this command is currently expected to fail):

```bash
ulimit -c 0
CARGO_BUILD_JOBS=1 cargo test --locked --features desktop \
  --test desktop_resilience screenshot_write_failure -- --ignored --nocapture
```

Suggested follow-up: ensure renderer cleanup executes on both success and failure, then propagate screenshot errors to a nonzero normal process exit.

### P2 — Large lists block the GTK main thread

Sorting 50,000 records and constructing the first 100 rows took a median **275.08 ms** in the debug build. Even a search with no matches took **81.90 ms**. At 10,000 records, a progress batch followed by redraw took **54.34 ms**.

The recorded code paths clone the selected Folder snapshot, clone all entries in `visible_files`, and repeatedly allocate case-folded names during comparisons. Pagination limits widget count but not the full-history preparation/sort. The worker receiver's 8 ms event-consumption budget also excludes the subsequent `flush_file_render` work. These are source-backed explanations for the measured synchronous cost, not proof that every component contributes equally.

Suggested follow-up: cache searchable/sortable keys, avoid full snapshot copies for view changes, and decouple history preparation from per-phase redraws. Re-measure release builds and frame latency before setting production performance budgets.

## Performance measurements

Environment: Linux 7.0.0-30-generic, i7-13700H, 20 logical CPUs, about 15 GiB RAM, GTK 4.22.4, libadwaita 1.9.1, Rust 1.98.0. The session had about 4.9 GiB available memory and fully used 4 GiB swap when inspected; results are local observations, not hardware-independent guarantees. Builds used `CARGO_BUILD_JOBS=1`.

The synthetic records have distinct, shuffled names/times/sizes and mixed English/Chinese names. Each normal measurement has one warm-up and five measured samples. Timings include synchronous handlers/model work/widget construction, **not the later paint/compositor frame**. All figures below are debug-build medians.

| File records | Pure time sort | Pure name sort | GTK name sort, first 100 rows | GTK search, no match | RSS at GTK sort stage |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 1.59 ms | 3.20 ms | 11.46 ms | 1.37 ms | 185.6 MiB |
| 10,000 | 20.02 ms | 43.29 ms | 54.18 ms | 15.33 ms | 207.9 MiB |
| 50,000 | 113.05 ms | 253.59 ms | 275.08 ms | 81.90 ms | 301.6 MiB |

- 100 alternating sorts at 10,000 records: median **54.12 ms**, maximum **57.63 ms**. RSS grew only **24 KiB** during the measured sequence.
- 32 measured batches of 64 progress events: median **54.34 ms**, maximum **55.38 ms** per batch including flush. Repeated events retained one live record, not 2,048 duplicate records.
- Rendering the sidebar: **4.51 ms** for 100 Folders; **46.42 ms** for 1,000 Folders.
- A separate idle window with two Folders was sampled twice for eight seconds after two seconds of settling: approximately **181 MiB RSS**, **0–0.125% of one CPU core**. CPU resolution is limited by `/proc` clock ticks; no active transfers were present.
- After the largest synthetic datasets were removed, RSS remained about **291.7 MiB**, versus **183.5 MiB** before stress. This alone does not distinguish allocator/GTK cache retention from leaks. The test does **not** certify leak freedom.

Reproduce the synchronous stress measurements:

```bash
ulimit -c 0
MIRELAY_DESKTOP_STRESS=1 CARGO_BUILD_JOBS=1 \
  ./dev/frontend/run.sh --workspace qa-stress-fresh --file-smoke-test
```

The environment variable is only consulted in the explicit, registry-isolated file smoke path. Synthetic history and Folder lists stay in memory and are restored after the diagnostic. `QA_PERF`, `QA_MEMORY`, and `QA_GUARDS` lines contain the measured output.

## Crash and recovery checks

These tests send actual `SIGKILL` to child processes created by the tests. They do not merely inject an ordinary returned error.

| Check | Result |
| --- | --- |
| Kill after writing part of a download | Partial staging file cleaned on restart; complete content received and verified; no premature ACK |
| Kill after durable content/state, before source ACK | Existing content reused; final state acknowledged without an additional received record |
| Kill after source ACK, before local acknowledged state | Reconciliation completed; one delivery remained; repeat receive stayed idempotent |
| Kill after persisting wallpaper `Running`, before launching the hook | Restored as `Uncertain`; automatic retry skipped; explicit uncertain retry succeeded using `/bin/true` |
| Kill desktop startup at 0 / 30 / 150 / 500 ms | Protected configs, registry, state and stored file bytes unchanged; file/sidebar smoke checks passed on reopening |
| Load a malformed Folder config | Desktop remained usable enough to render its error view; corrupted input and other protected files were unchanged |
| Save developer screenshot under a missing parent | **FAIL: process abort**, described above |

The ACK crash tests use the real filesystem-source pipeline, not a remote network server. Startup delays identify elapsed times, not exact internal startup phases. SIGKILL tests do not simulate a power outage or filesystem hardware failure.

## Misuse and input protection

Additional checks passed:

- 13 invalid/conflicting desktop argument combinations exit with code 2 before creating files.
- 25 invalid UI action targets do not change the selected sort/filter state.
- Negative and out-of-range Folder indices leave selection unchanged.
- A second task is rejected while busy; receive/settings buttons are disabled.
- Repeated sort-direction clicks keep exactly one direction selected; state follows the correct Folder.
- Five malformed/unsupported state inputs are rejected without rewriting them or creating an ACK.
- Oversized state/config files and a zero file-size limit are rejected.
- A symlinked state lock is rejected without changing the unrelated target.
- An unwritable state directory does not produce a premature ACK or overwrite prior state; recovery succeeds once permissions are restored. The permission case ran as a non-root user.

The existing suite additionally covers registry corruption and duplicate IDs, path overlap and symlink conflicts, reused device identities, shared queues, payload path traversal, invalid manifests, checksums, bounded retries, transfer-state events, tus offsets, and ordinary non-image deliveries.
